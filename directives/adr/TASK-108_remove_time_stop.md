# Architecture Decision Record: TASK-108 Remove Time-Stop (BE) Feature

## 1. Status & Context
- **Status**: Approved (Date: 2026-09-09)
- **Context**:
  - The ARES trading system currently includes an automatic, timer-driven break-even stop feature. When an open trade reaches a configurable duration (e.g., 30 or 45 minutes) without touching T1 (first target), the system automatically moves the stop-loss to break-even (BE).
  - This behavior has been identified as undesirable: it prematurely exits trades that have not yet hit T1, removing the opportunity for the trade to reach its target. The stop-loss should remain at its original entry level until a genuine T1 touch occurs.
  - The requirement (MANM-108) is to completely remove the automatic, timer-driven break-even stop feature from the system while preserving all post-T1 runner protection logic.
  - Related prior ADRs: `directives/adr/MANM-93_dhan-redis-api-removal-design.md` (architecture patterns), `directives/adr/TASK-005_dhan-pdh-pdl.md` (configuration patterns).

## 2. Decision
We will completely remove the automatic, timer-driven break-even stop feature from the ARES trading system.

### Key Architectural Decisions:
1. **Preserve Original Stop-Loss Until T1 Touch**:
   - An open trade's stop-loss must remain at its original entry-defined level until a genuine T1 (first target) touch occurs. The stop must NOT be moved merely because the trade has been open for a configurable duration.
   - This ensures trades have maximum opportunity to reach their targets without premature stop-outs.

2. **Preserve Post-T1 Runner Protection**:
   - The existing post-T1 protection logic (T1→BE trailing, `STOPPED_OUT_AT_BE` exit type) remains intact and unaffected.
   - Once T1 is genuinely touched, the system continues to manage the runner position with the established break-even trailing behavior.

3. **Remove `time_stop_minutes` from All Configuration Surfaces**:
   - Remove `time_stop_minutes` from config files, environment variables, Supabase metadata, and any runtime configuration loading.
   - No feature flags or replacement timers will be introduced.

4. **Remove `TIME_STOP` Exit Type from System Surfaces**:
   - Remove `TIME_STOP` from alert definitions, scoring logic, and ML labeling.
   - This exit type will no longer be generated by the system.

5. **No Database Schema Changes**:
   - No modifications to existing database tables (`ares_signals`, `trade_analytics`, `ml_collection`).
   - Historical data with `TIME_STOP` exit type remains unchanged in the database.

## 3. Interface & Contract Specifications

### Configuration Changes
- **Before**: `time_stop_minutes` parameter accepted in configuration (config files, env vars, Supabase metadata).
- **After**: `time_stop_minutes` parameter removed; any reference to it in configuration will be ignored or raise a deprecation warning.

### Exit Type Contract
- **Before**: Exits could be categorized as `TIME_STOP`, `T1_HIT`, `STOPPED_OUT_AT_BE`, `STOPPED_OUT_AT_T1`, etc.
- **After**: `TIME_STOP` exit type is no longer generated. Existing exit types remain unchanged.

### Trade Management Flow
```
[ Trade Entry ] ──▶ [ SL at Original Level ] ──▶ [ T1 Touch? ]
                                                       │
                                          Yes ─────────┼──────── No
                                          │            │            │
                                          ▼            │            ▼
                               [ BE Trailing ]        │    [ SL Remains at Original ]
                               [ STOPPED_OUT_AT_BE ]  │
```

## 4. Failure Modes, Observability & Rollback Strategy

### Failure Modes & Mitigations
| Failure Scenario | Behavior | System Impact |
|---|---|---|
| Configuration includes `time_stop_minutes` (legacy) | System ignores the parameter; logs a deprecation warning | No behavioral change; clean migration |
| Historical data contains `TIME_STOP` exits | Read-only; no transformation applied | Historical analytics unaffected |
| ML model expects `TIME_STOP` as a feature | Feature becomes unavailable; model retraining required | ML pipeline degrades gracefully |

### Observability
- **Alerts**: Remove `TIME_STOP` from alert definitions. Existing alerts for other exit types remain unchanged.
- **Scoring**: Remove `TIME_STOP` from trade scoring logic. Scoring will no longer penalize or reward based on this exit type.
- **ML Labeling**: Remove `TIME_STOP` from live runtime trade outcome generation. Historical records in `ml_collection` retain `TIME_STOP` mapped to `0` (loss) in `classify_ares_outcome` to ensure negative examples are preserved during offline retraining without introducing label bias.

### Rollback Strategy
- If the removal causes unexpected issues, the feature can be restored by reverting code changes and re-adding `time_stop_minutes` to configuration surfaces.
- No database rollback required (no schema changes).
